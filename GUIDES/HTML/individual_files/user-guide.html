What is Platform Atlas?

Platform Atlas is a configuration auditing tool built specifically for the Itential Automation Platform. Think of it as a knowledgeable colleague who knows exactly what a healthy IAP deployment looks like — it reads your configuration, checks it against a curated ruleset, and hands you a clear report showing what's right, what needs attention, and why.

Capture

Connects via SSH, MongoDB, Redis, and the Platform API to collect configuration data from every component of your deployment.

Validate

Runs your captured data through over 100 best-practice rules covering Redis, MongoDB, Platform, and Gateway — critical, warning, and info severity.

Report

Generates three HTML reports: a compliance overview, an operational analysis with log data, and an architecture & maintenance view.

Atlas is designed for both Itential Customer Success teams running quarterly health checks and customers who want to perform self-service validation at any time. Once you're set up, a full audit is just two commands: create a session, then run it.

Requirements

Atlas is a Python CLI tool that runs on the machine you use to connect to your IAP environment — typically your workstation or a jump host with network access to your servers.

  • Python 3.11 or later
  • SSH access to your IAP, MongoDB, and Redis nodes (key-based authentication recommended)
  • A MongoDB user with clusterMonitor on admin and read on the Platform database
  • A Redis user with +config|get, +info, +acl, +ping, +role ACL permissions
  • A Platform OAuth service account with read-only API access (apiread:Adapters, apiread:Health, etc.)
  • An OS keyring backend, or HashiCorp Vault with a KV v2 secrets engine
Install on your workstationAtlas works best installed on a workstation PC that has remote access to your IAP environment. It doesn't need to be on the same machine as IAP itself.

Installation

Atlas is distributed as a Python wheel file. Install it inside a virtual environment to keep it self-contained.

Install from a wheel file

Your Itential contact will provide a .whl file. Create a virtual environment, then install:

# Create and activate a virtual environment
python3 -m venv atlas-venv
source atlas-venv/bin/activate   # Windows: atlas-venv\Scripts\activate

# Install the wheel
pip install platform_atlas-1.6.4-py3-none-any.whl

# Verify it works
platform-atlas --version
✓
You're installedYou should see a version string like platform-atlas 1.6.4. If you get "command not found", make sure the virtual environment is active or that ~/.local/bin is in your PATH.

Headless Linux Setup

On a headless Linux server without a desktop environment, the default keyring backend stores credentials in plaintext. Atlas will warn you about this. To set up encrypted credential storage:

pip install keyring keyrings.alt pycryptodome SecretStorage

# If SecretStorage fails to build:
dnf install libsecret-devel python3-dbus

# Configure the encrypted file backend
mkdir -p ~/.config/python_keyring
cat > ~/.config/python_keyring/keyringrc.cfg <<EOF
[backend]
default-keyring=keyrings.alt.file.EncryptedKeyring
EOF

Alternatively, use HashiCorp Vault as your credential backend — it bypasses the keyring entirely.

First-Time Setup

The first time you run platform-atlas with no configuration, it launches an interactive setup wizard. You can also run it at any time with:

platform-atlas config init

The wizard has two phases. Here's what to expect at each step.

1
Global Settings

You'll set your organization name (appears on reports and serves as the default for new environments), your preferred color theme, and a couple of optional settings. These are saved to ~/.atlas/config.json and apply across all environments.

2
First Environment

An environment represents one IAP deployment — for example, "production" or "dev". The wizard walks you through three things:

  • Credential storage — Choose between the OS keyring (default) and HashiCorp Vault. See the Vault section for details if your organization manages secrets in Vault.
  • Connection credentials — Your Platform URI, OAuth client ID, Platform client secret, MongoDB URI, and Redis URI. All stored securely in your chosen backend, never in config files.
  • Deployment topology — Tell Atlas how your environment is laid out: Standalone (one IAP, one Mongo, one Redis), HA2 (multiple nodes), or Custom. You'll configure SSH access (user, key file, port) for each server.
At the end of setup, you'll be asked if you want to create another environment. If you manage dev, staging, and production deployments, set them all up now — or add them later with platform-atlas env create.

Environments

An environment is a named file that holds all the connection details and topology for one IAP deployment. You can have as many as you need — one per customer, one per deployment stage, whatever makes sense for your work.

Environment files live at ~/.atlas/environments/<name>.json. They store things like your Platform URI, OAuth client ID, deployment topology, and which credential backend to use. Sensitive values (passwords, URIs) are never written to the file — they stay in your keyring or Vault, scoped under platform-atlas/<env-name> so each environment's secrets are fully isolated.

Managing Environments

# See all environments (shows which is active)
platform-atlas env list

# Create a new environment (interactive wizard)
platform-atlas env create

# Copy an existing environment and adjust it
platform-atlas env create staging --from production

# Switch the active environment
platform-atlas env switch staging

# View details of an environment
platform-atlas env show production

# Edit settings (org name, URIs, topology)
platform-atlas env edit staging

# Remove an environment
platform-atlas env remove dev

One-off overrides

Use the --env flag to run a single command against a different environment without changing your active one:

platform-atlas --env dev preflight
platform-atlas --env staging session run capture
Environment resolution orderWhen Atlas starts, it looks for the active environment in this order: the --env flag → the ATLAS_ENV environment variable → the active_environment field in config.json → no environment (legacy mode).

Running an Audit

An audit in Atlas follows a fixed sequence. Each step feeds into the next, and all the results from a single audit live together in a session — a named directory under ~/.atlas/sessions/.

1

Preflight

Before you collect anything, verify that Atlas can reach everything it needs to. Preflight tests each service independently and tells you exactly what passed, failed, or was skipped.

platform-atlas preflight

It checks SSH connectivity to all nodes, MongoDB and Redis authentication, Platform API reachability, and config file readability. Fix any failures before continuing — a capture with missing connectivity will produce an incomplete dataset.

2

Create a Session

A session binds together an environment, a ruleset, and a profile — and holds all the files for one complete audit. When you switch sessions later, the full context switches with it.

# Interactive — walks you through environment, ruleset, and profile
platform-atlas session create prod-audit-q1

# Or specify everything upfront
platform-atlas session create prod-audit-q1 \
  --env production \
  --ruleset p6-master-ruleset \
  --profile p6-prod-standalone-gateway4

The session becomes active immediately after creation. If you made a mistake (wrong environment, wrong profile), you can fix it with platform-atlas session edit — but only before capture begins.

3

Capture

This is where Atlas goes out and collects data. You'll see a live progress display as each collector runs — system info, MongoDB status, Redis config, Platform API health, log files, and more. If one collector fails, the rest keep going.

platform-atlas session run capture

If a collector fails, Atlas offers a guided fallback to let you provide the data manually. Skip it with --skip-guided if you don't need it. You can also batch-import pre-collected files for air-gapped environments:

platform-atlas session run capture --manual --import-dir ~/atlas-files/

After capture completes, Atlas will ask if you want to run MongoDB aggregation pipelines for the operational report. These query live workflow and task data — accept if you want execution statistics in the report, decline if you only need the compliance data.

4

Validate

Validation runs your captured data through every rule in the active ruleset. Each rule produces a PASS, FAIL, SKIP, or ERROR result. Rules can depend on other rules — if a dependency fails, downstream rules are automatically skipped rather than producing misleading errors.

platform-atlas session run validate

After the primary ruleset runs, Atlas runs a set of Extended Validation checks that analyze patterns across the full dataset — adapter version coverage, log error rates, Redis ACL completeness, and more.

5

Report

Generates three HTML reports in one pass and opens the compliance report in your browser.

platform-atlas session run report
FileContents
03_report.htmlCompliance score, category breakdown, all rule results, extended validation findings
04_operational.htmlPlatform, webserver, and MongoDB log analysis; MongoDB pipeline metrics
05_arch.htmlAdapter states, Redis ACL, index status, IAG paths, architecture overview

All three reports share a header navigation bar so you can switch between them without leaving your browser. If you're on a headless server, find the reports at ~/.atlas/sessions/<name>/ and copy them to your local machine.

Run everything at once

Once you're comfortable with the workflow, run all three stages in one command:

platform-atlas session run all

Add --headless for automated or scripted runs — it suppresses all interactive prompts, guided fallbacks, and won't try to open a browser:

platform-atlas session run all --headless

Filtering log dates

You can narrow the log collection window during capture using date flags:

# Collect logs for a specific date range
platform-atlas session run capture --log-since 2026-04-01 --log-until 2026-04-21

When a date range is used, the operational report shows a banner indicating which window was captured. Normal capture behavior is unchanged when neither flag is provided.

Managing Sessions

Sessions are the primary unit of organization in Atlas. Each one represents a complete audit cycle and carries its own environment, ruleset, profile, and organization name — switching sessions restores the full context in one step.

Switching sessions

# Interactive picker — shows environment, org, and status for each
platform-atlas session switch

# Or switch directly by name
platform-atlas session switch prod-audit-q1

Viewing sessions

platform-atlas session list                     # All sessions with status
platform-atlas session show                     # Details of the active session
platform-atlas session show prod-audit-q1       # Details of a specific session

Editing session bindings

Made a mistake during session creation? You can change the environment, ruleset, or profile — but only before capture begins. Once capture starts, the session is locked to protect data consistency.

platform-atlas session edit

Comparing sessions

If you've run audits at different times, compare them to see exactly what changed:

platform-atlas session diff baseline-q4 current-q1

The diff report classifies each rule as Fixed, Regressed, Unchanged, New, Removed, or Skipped. It's the fastest way to demonstrate progress to stakeholders or catch regressions after a configuration change.

Exporting sessions

platform-atlas session export prod-audit-q1

This creates a ZIP archive containing the reports, session metadata, and a README. Raw capture data is redacted by default — add --no-redact if you need the full JSON for troubleshooting.

Cleaning up

# Delete a specific session
platform-atlas session delete prod-audit-q1

# Bulk-delete uncaptured sessions older than 30 days
platform-atlas session prune --older-than 30
platform-atlas session prune --older-than 30 --dry-run   # Preview first

The easiest way to select a ruleset and profile is the interactive setup command — it walks you through both in one step and is the recommended approach when creating sessions:

HashiCorp Vault Integration

If your organization manages secrets in Vault, Atlas can read credentials from a KV v2 secrets engine instead of the OS keyring. Atlas is strictly read-only — it never writes to Vault. Your team manages the actual secrets through the Vault UI, CLI, or API.

Vault connection settings (URL, auth method, path) are stored in the OS keyring under a vault_ prefix, keeping them off disk entirely. The actual credentials Atlas uses to run audits (Platform secret, MongoDB URI, etc.) live in Vault at your configured path.

To configure Vault as your credential backend during setup, select it when the wizard asks. To reconfigure an existing installation:

platform-atlas config credentials

Choosing an auth method

Atlas supports five authentication methods, split into two groups. If your organization's security policy doesn't require credential rotation, either Standard method is a fine choice. If credentials rotate automatically — or if you want them to — use one of the Automated methods.

Token Standard

You provide a Vault token directly. Atlas stores it in the OS keyring and uses it on every run.

Good for simple setups where the token is long-lived or you rotate it manually.

AppRole Standard

You provide a role_id and a static secret_id. Atlas stores both in the OS keyring and uses them to authenticate on every run.

Good for machine-to-machine authentication when the secret_id doesn't need to rotate.

AppRole (Wrapped) Automated

Instead of a raw secret_id, you store a wrapping token — a one-time-use token that Vault unwraps to retrieve the actual secret_id at connect time. The token is consumed on first use, so a stolen keyring entry can't be reused after Atlas has run.

Your pipeline or Vault admin generates a fresh wrapping token on a schedule and updates the keyring entry. Atlas handles the unwrap transparently.

Good when your security policy requires rotating secret_ids but you can't run a daemon on the Atlas host.

Token (file) Automated

Atlas reads a token from a file on disk at runtime. Vault Agent — a separate service from HashiCorp — runs on the same host, authenticates to Vault independently, and writes a continuously-renewed token to that file. You configure the file path once; after that, Atlas always finds a valid token with zero maintenance on your part.

The best fully-automated option. Set it up once with your Vault admin, then never think about credential rotation again. See Vault Agent Setup below.

Token (env) Automated

Atlas reads the VAULT_TOKEN environment variable at runtime. Nothing is stored in Atlas — your pipeline, systemd unit, or orchestrator is responsible for setting that variable before Atlas runs.

Good for CI/CD pipelines or orchestrated environments that already manage Vault tokens and inject them as environment variables.

Setting up Vault Agent (Token file method)

Vault Agent is a separate binary that HashiCorp distributes with Vault. Your Vault admin sets it up once on the Atlas host:

1

Install Vault Agent

Download and install the Vault binary from HashiCorp. The same binary serves as both the server and the agent.

2

Write an agent config file

Create a config file (e.g. /etc/vault-agent/atlas.hcl) with an auto_auth block pointing to your Vault instance and a sink block specifying the token file path:

vault {
  address = "https://vault.yourcompany.com:8200"
}

auto_auth {
  method "approle" {
    config = {
      role_id_file_path   = "/etc/vault-agent/role_id"
      secret_id_file_path = "/etc/vault-agent/secret_id"
    }
  }
}

sink "file" {
  path = "/run/vault-agent/atlas.token"
}
3

Run as a systemd service

Create a systemd unit so the agent starts at boot and stays running. Vault Agent automatically renews the token before it expires and re-authenticates if it ever expires.

4

Configure Atlas

Run platform-atlas config credentials, select Token (file), and enter the sink path (/run/vault-agent/atlas.token). Atlas will read a valid token from that file every time it runs — no further maintenance needed.

Troubleshooting

Atlas writes a log to ~/.atlas/atlas.log. For verbose output during a command, add --debug:

platform-atlas --debug session run capture

Frequently Asked Questions

Can I run Atlas against a production system safely?

Yes. Atlas is strictly read-only. It reads config files via SSH and uses read-only API operations on MongoDB, Redis, and Platform. It never modifies configuration, restarts services, or writes data to your IAP environment.

Some collectors failed during capture. Is my data incomplete?

Partial captures are completely normal. Atlas is designed to work with whatever it can collect. Failed collectors show as SKIP in the report, and the compliance score is calculated only against rules that had actual data to evaluate. If you have pre-collected files for the failed modules, import them with --manual --import-dir.

I have dev, staging, and production deployments. Do I need separate Atlas installations?

No — create an environment for each one, then create sessions bound to each environment. Switching between audits is a single platform-atlas session switch command.

I upgraded from a version before 1.5. Do I need to redo my setup?

No. Existing configurations, sessions, and environments all continue to work. Sessions created before v1.5 won't have bound rulesets or environments — they'll use whatever is globally active. You can backfill metadata with platform-atlas session repair.

Where does Atlas store its data?

~/.atlas/
├── config.json          # Global settings (no secrets)
├── atlas.log            # Application log
├── environments/        # One JSON file per deployment target
├── sessions/            # One folder per audit session
│   └── prod-audit-q1/
│       ├── session.json
│       ├── 01_capture.json
│       ├── 02_validation.parquet
│       ├── 03_report.html
│       ├── 04_operational.html
│       └── 05_arch.html
└── pipelines/           # Custom MongoDB pipeline definitions

I need to run Atlas on a schedule

Use --headless to suppress all interactive prompts, and pre-create a named session for the scheduled run:

platform-atlas session run all --headless

Make sure your credential backend works non-interactively. On Linux, this means either keyrings.alt (encrypted file backend) or Vault with the token_file or token_env auth method.
